There are engineering problems you discover because they are difficult.

And then there are the ones you discover when you are really, really lazy.

For me, it was QA.

I was temporarily assigned GUI testing work to learn a large enterprise application.

The assignment made sense. The business application had complicated workflows, hidden dependencies, and enough business rules to punish anyone who clicked through it without understanding the process and following the correct flow, and skipping any step would result in a painful list of validations later on that would make anyone reconsider their employment.

There was only one problem.

I did not want to keep doing these testing, especially not manually.

## The Job

Each testing request followed roughly the same routine.

Someone (either developer or product owner) would explain what the new change was and what needed to be tested. But to test these changes one had to reconstruct the existing business processes and arrive at the stage where the new change was introduced, then perform the testing considering multiple scenarios, capture screenshots and make a .docx evidence file. This was the only part of my job I hated. The clicking were repetitive, but the thinking around them were not.

Fortunately, I had already built a RAG chatbot (the one I built in Story 000) using the applications user manuals, FAQs and training video transcripts. Whenever I did not know how to complete a business flow, I asked the chatbot, and it told me what to do and how to do it.

But I still had to perform the manual labor. And again, I hated how much of my time and efforts disappeared into something that was pretty meaningless to me and my future.

## My Completely Reasonable Response

I decided to build my replacement, a machine that would do this job for me.

The first version of the idea was simple:<br>
Give a Vision Language Model capable of Computer-Use the current screenshot -> Tell it what needs to be achieved -> Let it decide the next action -> Orchestrate the action -> Capture the new screen -> Repeat.

Although the <a href="https://openai.com/index/introducing-gpt-5-4/">Open AI GPT 5.4 with its advertised SOTA Computer Use and Vision</a> capabilities was really attractive to me, I had to find an open-weight alternative as I needed a working prototype and PoC first to show the management, only then I would get approval for GPT 5.4 API subscription. So I set out on my journey to find the best VLM with CUA capability for my use case while fitting on a 12 GB VRAM card.

That led me to Qwen3-VL-8B-Instruct. I downloaded the model, loaded it through LM Studio, and began with a very basic isolated validation. I gave the model screenshots of the application and asked questions such as:<br>
- To complete this goal, what is the next atomic action needed?
- Has the previous action changed the interface as expected?

And the answers were good enough to prove that a tighter system instruction would make the outputs more precise and robust. So I gave it a precise system prompt and forced it to return one atomic action at a time.

Because I had learned, when a model of this size is operating software, asking for an entire sequence of actions is a fantastic way to let one bad assumption ruin everything that follows. Asking for one action at a time at least limits the damage to one click.

But another problem arises. The VLM was able to answer what atomic action needed to be done and what GUI element needed to be acted upon. But it failed badly to predict the exact coordinates where the action needed to be done. I had the execution brain, but was lacking a nervous system and motor control. 

The second version:<br>
Another rabbit hole led me to <a href="https://huggingface.co/Salesforce/GPA-GUI-Detector">Salesforce/GPA-GUI-Detector: A YOLO-based GUI element detection model for detecting interactive UI elements (icons, buttons, etc.) on screen for GUI Process Automation</a>. Perfect just the piece I needed. This would literally become the eyes of my replacement. But it only detected the elements bounding box and their coordinates, not the text inside that bounding box. To read what was in the bounding box, i used <a href="https://huggingface.co/microsoft/trocr-base-printed">TrOCR</a>. Now I could get the GUI element's bounding box coordinates along with what was written inside the bounding, if text the OCRed text else a generic 'icon' placeholder. The code to extract 2d coordinates (x, y) and text of each detected GUI element and build a UI map, is <a href="https://github.com/suwesh/Project-REKNOW/blob/main/Implementation%3A%20Autonomous%20GUI-Based%20QA/Execution%20Intelligence/wsl-perception-service/eyes_of_gui_qa.py">available here</a>. 

But I was still naive to think that such a large JSON of the UI Map, aling with the screenshot and system prompt giving it to the VLM in one forward pass would be feasible. It was really expensive. Especially on my constrained hardware. And even after paying that expensive cost, the VLM was still hallucinating(even with controlled temperatuire and top_p) exact coordinates maybe because the sole size of the UI MAP was overwhelming to it. That gave birth to the third verson.

The third version:<br>
After doing vibe feasibility check, i decided to keep the VLM output only the high level intent of what mouse or keyboard action needed to be performed and on what element shown in the GUI. I lifted the burden of coordinates resolving from the VLM and decided to make a deterministic resolver which would take the VLM output (actomic action intent) and the UI Map (GUI element text + bounding box coordinates with calculated center coordinates) and <a href="https://github.com/suwesh/Project-REKNOW/blob/main/Implementation%3A%20Autonomous%20GUI-Based%20QA/Execution%20Intelligence/windows-runtime/tools/actor.py">this new code</a> would output the action and the location where to perform the action. Ofcouse this new code needed to be perfected, mainly because of the complexity of this business application's GUI, and the TrOCR did some spelling mistakes, and the icons were not really recognized but for the prototype there was no flow to click a icon without text labels. Omnly needed to click buttons which had text and fill values in fields, for this this code was surviving. also There were multiple search bars, and elements with same text. Hence i implemented a fuzzy logic if no exact match was found. This new resolver was based on pure basic 2d Coordinate geometry. 

And now the execution sub system was working. The VLM (brain) decided on a high level which elemnent to act on and the action. The eyes mapped the whole screen into a 2D plane with the detected text of each element and its coordinates as if each element were a point (x, y) on the plane. The actor was the motor control or what?? and then it worked .

But it was still semi autonomous. Give it a business steps and it would proceed to perform the execution and ijntract with the enterprose GUI. But Now i needed to automate the front part.
