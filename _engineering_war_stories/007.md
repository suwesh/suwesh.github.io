_"Make the agent faster."_ That was essentially the requirement.

The agent used an open-weight reasoning model and was deployed on an AWS EC2 instance with a single NVIDIA A10G. It was the chatbot I built in Story 000, which had since evolved into an agent (Story 004). The majority of the user-visible latency came from the multi-step LLM generations required to fulfill a single user request.
```text
User Request ---> Planner LLM Reasons & Generates Tool Calls ---> Orchestrator executes tool calls ---> Enterprise Application API calls ---> Generator LLM receives tool results, reasons, and then streams the first user-visible token
```

Of course I had streaming tokens enabled, but it was still not enough for the managers. So I changed the UX to show the reasoning tokens in a mini box, similarly to how LM Studio's GUI does it. This way, the user could see beyond the opaque "Thinking..." text and think, okay, something is happening and it's not stuck. But the managers said this UX would make the user more confused, as the user base was not even slightly tech savvy. So I reverted this UX change.

Now how was I supposed to mitigate this obvious constraint? If the model was going to generate a long reasoning trace, you couldn't simply make the text appear faster by wishing it into existence. Even though the network-bound external API calls did add noticeable latency, it was negligible compared to the Planner and Final LLM reasoning completion. Oh, I should mention that the current autoregressive generation rate was around ~90 tok/s.

Thank god I faced this performance optimization problem, which turned me into something more than a mere vLLM inference engine user, and sent me down the currently infant inference engineering rabbit hole. I did my research and discovered speculative decoding, which promised to speed up my LLM generation by ~2×, at least. And, thanks to the coincidence that I was using Gemma 4 E4B IT, there was a readily available dedicated MTP drafter model trained by Google, alongside the embedding and distribution of the model I was already using. I had previously stumbled upon this Gemma 4 E4B IT assistant checkpoint, but its use was not so clear to me back then, when I was looking for models to upgrade the chatbot into this assistant.

After clearing speculative decoding at the theoretical concept level, and gathering every element for a smoke test, I was ready to implement speculative decoding on my Workstation. I passed the newly learned speculative config:`mtp ...`vLLM args, and the new MTP vLLM deployment was live. I sent a couple of requests and saw in the vLLM telemetry: average generation rate had bumped up to ~200 tok/s.

## Damn. I felt like I had strapped a supercharger onto my car.
